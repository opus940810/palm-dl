# Publishing PalmDL on GitHub (with a citable Zenodo DOI)

GitHub and Zenodo solve different problems and are normally used together:

| | GitHub | Zenodo |
|---|---|---|
| Purpose | living code, issues, pull requests, visibility to developers | immutable archive, DOI, long-term preservation |
| DOI | none by itself | yes (DataCite) |
| Permanence | history can be rewritten, repo can be deleted | fixed snapshots, versioned |
| Size | <100 MB per file, ~1 GB per repo | 50 GB per record |
| Peer review | public, or private with invited reviewers | public snapshot |

Recommended pattern: **GitHub is the working repository; Zenodo auto-archives each
GitHub release and mints a DOI.** The manuscript cites the DOI; reviewers can read
the code on GitHub.

A ready-to-push tree is generated by `python src/make_github_bundle.py` into
`dist/github` (18 MB, 143 files). It contains code, docs, figures, manuscript,
the canonical folds and summary tables, and deliberately excludes the large
generated artifacts that live in the Zenodo archive.

## 1. Create the repository

Either use the web UI (github.com → New repository → `palm-dl`, public or private,
no README) or GitHub Desktop ("Add existing repository" → select `dist/github`).

## 2. Push the tree

Git is not installed on this machine, so run these commands on a machine that has
it (or use GitHub Desktop, which does the same thing):

```bash
cd dist/github
git init -b main
git add .
git commit -m "PalmDL 1.0.0: leakage-aware benchmark, model, scan, service"
git remote add origin https://github.com/<ORG>/palm-dl.git
git push -u origin main
```

Check that the repository is ~18 MB and that `models/`, `results/literature/xml/`
and `results/structure/af/` are absent (they are in `.gitignore`).

## 3. Tag and release

```bash
git tag -a v1.0.0 -m "PalmDL 1.0.0"
git push origin v1.0.0
```

Then on GitHub: Releases → Draft a new release → choose tag `v1.0.0` → paste the
release notes → **Publish release**.

## 4. Link Zenodo (one-time, then automatic)

1. Sign in to https://zenodo.org with GitHub (or ORCID).
2. Settings → GitHub → find `palm-dl` → toggle **On**.
3. Back on GitHub, (re)publish the `v1.0.0` release.
4. Zenodo archives the snapshot and shows a DOI. Wait a minute, then reload.

Zenodo gives two DOIs:

- **concept DOI** — always resolves to the latest version; use it in the paper and README.
- **version DOI** — pins exactly v1.0.0; use it when you need to cite the analysed snapshot.

Add the badge to `README.md` (already placeheld as `[ZENODO-DOI]`):

```markdown
[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.XXXXXXX.svg)](https://doi.org/10.5281/zenodo.XXXXXXX)
```

## 5. Fill the placeholders

Replace `[ORG]`, `[ZENODO-DOI]`, and the author fields in `CITATION.cff`,
`.zenodo.json`, `README.md` and the manuscript's Data-and-code-availability
paragraph.

## 6. Private-until-acceptance (optional)

If the paper is under review and you do not want the code public yet:

- keep the GitHub repo **private** and add the editor/reviewers as collaborators, or
- create an anonymous read-only mirror with https://anonymous.4open.science and cite
  that link in the manuscript, or
- archive privately on Zenodo (restricted access) and share the private link.

Many journals now require public code at submission; check the target journal's
policy. The safest default is public repository + Zenodo DOI at submission.

## 7. Large artifacts

These are in the Zenodo record, not in git:

| Artifact | Size | Where |
|---|---|---|
| `results/preds_cv_all.csv` (out-of-fold predictions) | 43 MB | Zenodo |
| `results/scan/all_scores.csv` (proteome-wide scores) | 34 MB | Zenodo |
| `data/raw/*.tsv` (UniProt snapshot) | 23 MB | Zenodo |
| `models/*.joblib`, `*.pt` | 207 MB | regenerate (3–10 min) or Zenodo |
| `results/literature/xml/` (992 full texts) | 187 MB | **not redistributed** (copyright) |
| `results/structure/af/` (AlphaFold PDBs) | 155 MB | downloadable from AlphaFold DB |

If you want the model binaries in the repository, put them in a GitHub Release
asset rather than in git history.
